# Manufacturing Mayhem: Design of a Coordinated Robot Fleet

**Student:** [name, number] **Module:** COMP41400 **Date:** [ ]

## 1. Organisation and responsibilities

The system uses a **central coordinator** organisation with two agent types on top of the supplied CArtAgO environment.

| Agent | Instances | Role | Information maintained |
|---|---|---|---|
| `MyStrategy` (coordinator) | 1 | Discovers resources, assigns orders to packaging points, decides which robot performs which transfer, triggers workstation operation and order delivery | Resource lists, product → workstation map, `busy(robot)`, `busyPP(packagingPoint)`, `usedAp(accessPoint)`, a task-id counter and the pending task table `task(id, robot, from, to)` |
| `MyRobot` (controller) | 1 per robot | Executes one transfer at a time, resolves short-term location conflicts, decides when to charge | Its own location, held item and energy (observed from its Robot artifact), the `travelDistance` option (read from the factory artifact) and the largest transfer energy cost it has measured |

The supplied `Main` and `core.Factory` agents only start the system and build the environment; they are not modified.

Decisions are split by the information they need. **What** should be done and **by whom** is decided by the coordinator, because only it sees all orders, workstations and robots at once. **How** a transfer is physically carried out, including waiting for an occupied location and charging, is decided by the robot, because the robot can observe its own energy and position directly. The **environment artifacts** decide what is legal. They enforce capacity (one robot per location, one item per robot), energy limits and recipes. Agents never bypass them.

The coordinator obtains information by observing artifact properties: the `factory` artifact's configuration lists, `inputsNeeded` and `state` of workstations, `outstanding` at packaging points, and the order counters. It also relies on messages from robots. No resource names are hard-coded, so the same agents run on any scenario that has single-stage recipes.

## 2. Coordination mechanisms

**Task allocation.** Before sending a request, the coordinator claims a free robot by adding `busy(r)`. The claim is released only when the robot reports `transferred`. This makes double allocation impossible, because a robot is never offered two tasks at once.

**Communication protocol.** Each transfer carries a unique task identifier and uses three messages: `request transfer(id, from, to)`, then `inform delivered(id)` once the item has been unloaded, then `inform transferred(id)` once the robot has parked and is available again. If any step fails, the robot replies `failure transfer(id, from, to)`, so the coordinator never blocks on a reply that will not come. Within one input batch the route alone would be unambiguous, because `usedAp` gives each input a distinct access point. Replies are still matched by sender and task id, because concurrent tasks in different batches can share a route (for example, the two items of a two-item order both travel from ws1 to pp1). Separating *delivered* from *transferred* lets production continue while robots are still driving back.

**Production dependencies.** For each product, the coordinator selects the workstation whose `output` matches and reads its missing inputs. It assigns each missing input to a different access point and a different robot and sends all requests together. It then waits at a **barrier** until every input has arrived, operates the workstation, and dispatches the output to the packaging point.

**Shared resources.** Access points are reserved for the current batch through `usedAp(ap)`. Packaging points are reserved per order through `busyPP(pp)`. Locations are the remaining contention point: `free(location)` is only a check, so a robot that finds its target occupied waits and retries instead of failing. Robots always park at their own charger, so they do not block work locations.

**Concurrent activity.** Orders are pipelined. Once the output of an order has been dispatched, the coordinator immediately assigns the next order to another packaging point. Delivery of the previous order is completed event-driven: when the `delivered` message for its last item arrives, the handler calls `deliver()`.

## 3. Operational decisions

**Incoming orders.** The main loop continues while orders are waiting, still to arrive, or assigned but undelivered. When nothing is waiting it polls every 500 ms, so orders that arrive during the run are picked up.

**Charging.** After each transfer a robot parks at its charger and recharges only if its energy is below a *reserve* that covers one more transfer and the return journey. The robot reads the scenario's `travelDistance` option to choose how the reserve is set:
- *travelDistance off* (easy-02, easy-04): every move costs 100, so the worst case from the charger is three moves (300) plus load and unload (100). Both handling steps also require at least 100 energy, so the reserve is 400. With 800-energy robots this means one charge every two transfers instead of after every transfer.
- *travelDistance on* (easy-03, all medium and hard scenarios): move cost depends on distance, and agents cannot query distances directly. The robot therefore measures each job's energy use (energy when leaving the charger minus energy on return) and sets the reserve to the largest value observed plus a margin of one handling step (50). Until it has measured a trip, it charges to full before every job. If the reserve reaches its maximum energy, it simply charges to full each time.

**Failures and stalls.** A failed robot action is reported with its task id, the robot is released, and the coordinator's barrier is unblocked. Because the workstation's `inputsNeeded` is read again afterwards, a missing input is requested again. The failed robot stays where it failed and keeps any item it was holding; recovering that item is not designed.

**Assumptions and expected limitations.** Each product is made by one workstation in one stage. Two-stage recipes that need storage buffering (medium-07) are outside the initial design. Mixed single-stage products (medium-08) fit the product-to-workstation map, but only one order is advanced at a time, so several workstations are not used in parallel (this also limits medium-05). Location retries are bounded. The measured reserve can underestimate a longer route the robot has not driven before, so a first long trip may fail for lack of energy. A robot that fails away from its charger may block that location.

## 4. Worked interaction example

The example is easy-02: two robots, two access points, one workstation, two packaging points (see Figure 2).

1. The coordinator assigns order-1 to pp1. `outstanding(pp1)` returns `[apple-pie]`; ws1 makes apple-pie and needs `[apples, pastry]`.
2. It retrieves apples at ap1 and pastry at ap2, claims r1 and r2, and sends `transfer(t1, ap1, ws1)` and `transfer(t2, ap2, ws1)` together.
3. Each robot loads at its access point and unloads at ws1. If ws1 is occupied, the second robot waits and retries. Each robot sends `delivered`, and once both have arrived the coordinator calls `operate(ws1)`.
4. Because a move reserves its target on departure, r2 cannot leave for ws1 until r1 has left it (12 s). r1 is therefore back at its charger at about 16 s, before ws1 finishes. Its 400 energy equals the reserve, so it does not charge; it sends `transferred(t1)` and is released.
5. When ws1 reaches `done`, the coordinator claims the released r1 and sends `transfer(t3, ws1, pp1)`. It then immediately assigns order-2 to pp2 and starts fetching its inputs.
6. When the pie reaches pp1, the `delivered(t3)` handler sees an empty `outstanding` list and calls `deliver(pp1)`, which frees pp1 for a later order.
7. r1 returns with 0 energy, below the reserve, so it charges to full before sending `transferred(t3)`.

## 5. Design rationale and evaluation plan

A central coordinator suits this environment. State is already centralised in artifacts, the scenarios contain at most six robots, and the main risks are double allocation and missed dependencies, both of which are easiest to prevent with a single decision point. The trade-offs are a single point of failure and a bottleneck if the fleet grows. Robots keep local autonomy (retrying, charging) to limit that load.

**Alternative considered: Contract Net.** The coordinator would announce each transfer and robots would bid using what they can observe locally: their current location, energy and the trip costs they have measured (agents cannot query distances directly). This uses local knowledge better and would help when `travelDistance` is enabled. However, it adds a negotiation round to every task and requires bids to be managed while robots are committed elsewhere. In the two required easy scenarios travelDistance is off, so every robot has the same travel cost and the extra messages buy little. All fleets have at most six robots. Contract Net becomes attractive where travelDistance is on (easy-03, the medium and hard scenarios), and it is the main candidate extension.

**Evaluation plan.** Three versions will be compared on the same scenario files and seeds: `BasicStrategy`, a sequential version of this design, and the parallel, pipelined version.

| Scenario | Question | Metrics |
|---|---|---|
| easy-02-two-robots | Are both robots used concurrently? | makespan, per-robot busy time, load balance |
| easy-04-steady-arrivals | Are new orders picked up promptly? | order waiting time, completed orders, idle time |
| medium-09-tight-energy (travelDistance on, 650 energy, charge rate 75) | Does the measured reserve avoid running out of energy without charging more than needed? | charging time, failed operations (energy), makespan |

For each run I will record the scenario, seed, strategy version and controller substitution. I will save the simulator's Summary, and report incomplete runs together with their cause.
